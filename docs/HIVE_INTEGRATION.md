# Bear Hive integration

The Hive tab hosts the existing standalone Bear Hive planner in a same-origin iframe, preserving its own green identity, controls, CSS, map engine, templates, attendance and exports. React styles remain inline. Vendored source: caroline3543/Bear-Trap-Calculator, commit 59a9ccc9a7395175c94c4da50c3bf3caa0f16e68, bear-hive-planner/dist. The original planner remains independently deployed and unchanged.

Each state and case-sensitive alliance tag has its own storage key: bear-hive-intel:state:<state>:alliance:<encoded-tag>, with -history and -dark companions. The old standalone bear-hive-v1 key is neither read nor changed. To migrate a saved standalone plan, download its backup there and restore it through Plan settings in the matching integrated workspace. Planner backups are separate from the main roster JSON export.

React sends only a minimal roster (local ID, chief ID, exact name, furnace and valid reported coordinates) through origin/source-checked postMessage. No session tokens, secrets or full provider payloads are sent. Both ends enforce state and alliance identity. An update matches chief IDs, preserves planner IDs, placements, locks, notes and attendance, adds new members to Other players, never deletes missing members, and only replaces reported coordinates with an equally/newer dated observation. Unknown or duplicated chief IDs are excluded from the roster bridge. Cross-workspace backups are rejected.

Reported locations use validated profile coordinates, not a guessed city layout. The map shows retrieval timestamps; provider caching still applies. It is separate from planned positions and has no live map, shield or marching feed. The location detail links to the player profile. Bulk location fetch is described below. There is no background scanning. Bulk location fetch starts only when requested with the button. Traps, banners, HQ and other structures are not inferred from player coordinates.

Vendored changes are limited to: namespaced KEY and share URL query preservation in app.js; bootstrap/validation guard/message bridge scripts referenced by index.html. Standalone gesture and model code is retained. An inline embedding style in index.html hides duplicate headings and sizes the viewport to the embedded frame.

Validation: node --test tests/*.test.js; npm run build; the original planner's 12 test/*.test.cjs model suites against a CommonJS scratch copy of the vendored files. Browser fixture uses synthetic records only and passed phone/desktop loading, templates, dark mode, expansion, roster preservation, location selection, alliance/state isolation and reload persistence with zero page errors. Physical iPhone Safari and authenticated live provider refresh require separate verification.

Saved-roster UX: opening Hive or changing the selected roster synchronizes members automatically; no manual update button or provider request is needed. Locate all cities switches to the recorded-location map and resets its zoom/selection, fitting every available coordinate for the selected state/alliance. Missing coordinates are counted and listed. Planned slots are never changed by locating cities.

Bulk location fetch: Fetch all locations explicitly requests the existing authenticated proxy's base-only player endpoint once per valid saved alliance member, sequentially. It never creates or removes roster records. Each response must match the chief ID and state and contain a valid paired coordinate and retrieval time. Only providerStats.locationObservation changes, retaining profile data and its original source dates; older/missing coordinates keep their previous observation. Saved results update the map and planner bridge automatically. The provider may return cached data, so this is not a live game-map feed.

Progress reports checked/saved/missing/failed counts with per-player errors. Stop prevents further requests and discards the pending response; the current transport can take up to the existing proxy timeout to settle. Changing state/alliance or leaving Hive cancels application of pending results. Authentication and quota errors stop the queue without retry. Fetching locations leaves planned city slots, locks and attendance intact. JSON/cloud and the existing providerStats XLSX cell preserve the independent observation without database schema changes.

Bulk-fetch validation: six additional service tests cover response validation, non-destructive updates, latest-record merges, selected-alliance isolation, sequential requests, partial errors, cancellation, and auth/rate-limit stopping. The browser fixture stubs the existing proxy client, checks fetched coordinates appearing, missing-location retention, Stop behavior and unchanged planner notes. No real player lookup or authenticated live-provider refresh was performed by these fixtures.
